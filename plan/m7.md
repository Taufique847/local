# 4. M7 SERVICE DATA MODEL

Create or standardize a Service model.

Recommended structure:

```text
Service
├── _id
├── businessId
├── name
├── description
├── durationMinutes
├── startingPrice
├── status
├── category
├── isEmergencyService
├── createdAt
└── updatedAt
```

Field rules:

### businessId

Required.

References the Business.

Every service MUST belong to exactly one business.

Never trust businessId sent by the frontend.

Always derive the business from the authenticated user.

---

### name

Required.

String.

Trim whitespace.

Reasonable maximum length.

Example:

```text
AC Repair
```

---

### description

Optional.

Example:

```text
Diagnosis and repair of residential air conditioning systems.
```

---

### durationMinutes

Optional.

Number.

Examples:

```text
60
90
120
```

Must be positive when provided.

This field will later be used by the appointment scheduling system.

Do NOT build appointment scheduling in M7.

---

### startingPrice

Optional.

Number.

Represent USD.

Example:

```text
149
```

Do not create a complicated pricing engine.

This is only a basic starting price for future quoting/AI/booking workflows.

Do not hardcode currency conversion.

---

### status

Use:

```text
active
inactive
```

Default:

```text
active
```

Inactive services should remain in the database.

Do not permanently delete services by default.

---

### category

Optional.

Examples:

```text
Cooling
Heating
Maintenance
Installation
Indoor Air Quality
Ductwork
Emergency
Other
```

Keep this flexible.

Do not build an advanced category-management system.

---

### isEmergencyService

Boolean.

Default:

```text
false
```

Example:

```text
Emergency HVAC Repair
```

can have:

```text
isEmergencyService = true
```

This will later help the AI Employee identify emergency service requests.

Do NOT build emergency call routing yet.

# 6. SERVICE API ARCHITECTURE

Create:

```text
/api/services
```

Recommended endpoints:

### GET

```http
GET /api/services
```

Return paginated services for the authenticated user's business.

---

### GET SINGLE

```http
GET /api/services/:id
```

Return one service.

Verify that the service belongs to the authenticated user's business.

---

### CREATE

```http
POST /api/services
```

Create a service.

Example request:

```json
{
  "name": "AC Repair",
  "description": "Residential AC diagnosis and repair.",
  "durationMinutes": 90,
  "startingPrice": 149,
  "category": "Cooling",
  "isEmergencyService": false
}
```

Do NOT accept businessId as a trusted ownership field.

---

### UPDATE

```http
PATCH /api/services/:id
```

Allow editing service information.

---

### STATUS

```http
PATCH /api/services/:id/status
```

Example:

```json
{
  "status": "inactive"
}
```

Only allow:

```text
active
inactive
```

---

### DELETE / ARCHIVE

If deletion is implemented:

```http
DELETE /api/services/:id
```

Prefer soft deletion/archive behavior.

Do not permanently remove operational history unnecessarily.

If a service has future references, preserve historical records.
